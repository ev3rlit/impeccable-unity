# Delight

## Use and input
Add a small product-specific moment to a named meaningful event, such as earned progress, recovery or first success. It is not permission to celebrate every click.

## Read
Read unity-design.md, unity-csharp.md, unity-review.md and design-policy.md, the event source, repeat frequency and motion/audio preferences.

## Work
1. Find a real opportunity tied to the product's world and user achievement. Define one moment and the ordinary interactions it must leave quiet.
2. Choose a concise visual/copy/feedback treatment that reinforces state, not unrelated confetti, fake progress or hidden functionality.
3. Implement from the existing authoritative event, without duplicate rewards, delays or blocking completion. Respect repeated-use fatigue, dismissal and reduced motion.
4. Use sound only with explicit opt-in/established project consent and mixer policy. Clean up feedback on screen changes and canceled operations.

## Boundary and output
Edit the selected feedback and existing integration point. No gameplay feature, reward economy change, forced delay, new tracking or surprise audio.

## Verify and fallback
Trigger success, failure/cancel and repeated events; ensure feedback never creates another action. Without Editor/event access, finish only verifiable source changes and distinguish expected feedback from observed runtime evidence.

## Official example and Unity transfer

Read the [delight Before/After case](before-after-cases.md#delight) for the source, concrete problem, preserved properties and acceptance criteria. The example teaches a correction, not an art preset. Keep unrelated appearance and behavior unchanged; make the named improvement observable.
