# Init

## Use and input
Use once to establish durable product truth, or to fill identified context gaps. Input is the selected Unity project and any existing brief, not a request to choose a palette. Reuse confirmed facts; ask only about material unresolved audience, purpose, capabilities, devices, terminology or constraints.

## Read
Read unity-platform.md and design-principles.md, existing PRODUCT.md, project instructions, manifest, representative UI and supplied evidence. Existing code answers stack questions; do not ask a Unity project to select a web framework.

## Work
1. Establish the actual product, user situation, first useful action, input devices, localization/accessibility needs and binding commitments.
2. Separate evidence from inference. Confirm new inferred product facts with a concise question round when needed; an unanswered question is not consent. When no answer mechanism exists, mark assumptions/open decisions explicitly instead of inventing certainty.
3. Write confirmed facts and unresolved decisions into PRODUCT.md: platform/stack, users, purpose, positioning, operating context, capabilities/constraints, brand commitments and evidence that genuinely exists. Preserve existing sections outside scope.
4. Record Unity UI Toolkit and the actual project/Editor facts without hardcoding the research version. Recommend the next relevant command in conversation.

## Boundary and output
Only PRODUCT.md is an intended write. No DESIGN.md, visual-world selection, scene setup, new UI, hidden config or browser live setup. Volunteered binding visual constraints can be recorded without expanding them into a style exercise.

## Verify and fallback
Compare statements against evidence and ensure no unconfirmed claims slipped in. A missing Editor does not block product-context writing; mark runtime facts that source cannot establish. Return the product file and remaining decisions, not a UI implementation.

## Official example and Unity transfer

Read the [init Before/After case](before-after-cases.md#init) for the source, concrete problem, preserved properties and acceptance criteria. The example teaches a correction, not an art preset. Show the requested brief or document; a planning/documentation command does not authorize a UI redesign.
