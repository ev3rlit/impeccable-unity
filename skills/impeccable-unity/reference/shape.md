# Shape

## Use and input
Plan a named screen, feature or flow before code. Resolve task, audience, outcome, realistic content, fidelity, constraints, untouched areas and important states. A clear request supplies decisions; do not repeat settled questions.

## Read
Read design-principles.md, unity-design.md, unity-uxml.md and project context. Inspect the incumbent UI before deciding this is a new identity. Check devices/input rules when interactions are in scope.

## Work
1. Ask a compact round about material gaps. State the likely interpretation and invite correction rather than offering canned aesthetics.
2. Establish action order, information hierarchy, focus/navigation, empty/error/loading states, data ranges and device adaptation intent.
3. For a new/open screen use unity-design.md's visual authority and meaningful concept-choice process. A local refinement inherits its identity. Reuse discovery; do not begin persistence or implementation.
4. Present a concise brief: job/audience, outcome, selected direction, scope, states/ranges, interaction/layout and open decisions. Obtain necessary confirmation/corrections, then stop.

## Boundary and output
Return the brief in conversation. No UXML, USS, C#, scene changes, PRODUCT.md/DESIGN.md writes or persistent direction contract. A separate save/implementation request can authorize those later.

## Verify and fallback
Check that a builder can implement without inventing game rules or missing states. Without screenshots/Editor, ground structure in source and label appearance assumptions; do not claim a rendered preview. If a required answer is missing, keep that decision open instead of assuming approval.

## Official example and Unity transfer

Read the [shape Before/After case](before-after-cases.md#shape) for the source, concrete problem, preserved properties and acceptance criteria. The example teaches a correction, not an art preset. Show the requested brief or document; a planning/documentation command does not authorize a UI redesign.
